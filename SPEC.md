# SPEC — Node Flow Board

Визуальный редактор потоков (n8n-подобный) с локальным исполнением на Node.js.
Документ — задание для агента. Делай строго по нему; при расхождении с привычками n8n — приоритет у этого документа.

---

## 1. Цель

Веб-приложение: холст с нодами, соединения между портами, редактор выбранного блока (параметры + код подсвечен + CSS блока), запуск workflow локально в отдельном Node.js-процессе, финальный блок с результатом.

## 2. Решения (зафиксированы, не пересматривать без запроса)

1. **Исполнение:** один workflow → один Node.js-процесс (process-runner). Задел на «блок → отдельный процесс» в будущем, но **не** в MVP.
2. **Данные между портами:** один JSON на порт. **Без** items/батчинга.
3. **Custom CSS:** оформление самой ноды на холсте (background, border, порты). Scoped на ноду.
4. **Хранение:** своя JSON-схема (ноды, рёбра, позиции, оверрайды).
5. **JS разрешён** (no-js требование сюда НЕ распространяется).
6. **Стек:** Next.js (App Router) + shadcn/ui. Тема (light/dark) и i18n — с самого начала.
7. **Типы блоков добавляются кодом (TS-классами), НЕ пользователем в UI.** Исключение — встроенный **Code-блок**: внутри него пользователь пишет JS (как Code node в n8n). Этот код исполняется в vm-контексте, глобалы которого = явно прокинутый нами `env` (whitelist). См. §5a.

## 3. Модель блока (ООП)

Все блоки — TS-классы. Наследование — родное (`extends`), цепочки любой глубины.

```ts
abstract class Block {
  static type: string              // уникальный ключ в реестре
  static label: string
  static icon: string              // имя tabler-иконки
  static category: string
  static ports: PortsDef           // дефолтные порты
  static params: ParamSchema[]     // схема настроек → авто-UI
  static defaultCss: string

  abstract run(
    inputs: Record<string, Json>,  // { in0: json, in1: json }
    params: Record<string, Json>,  // значения из node.params
    ctx: RunContext
  ): Promise<Record<string, Json>> // { out0: json } — ключи = id out-портов
}
```

- Наследник переопределяет статику и/или оборачивает `run` через `super.run()`.
- **Важно (изоморфность):** классы импортируются и в `apps/web` (браузер), и в `packages/engine` (node). На уровне модуля блок НЕ должен импортировать node-only или browser-only API. Node-only код допустим только внутри тела `run`. Статические метаданные обязаны быть изоморфными.

### Реестр

```ts
// packages/blocks/src/registry.ts
export const registry: Record<string, typeof Block> = {
  source: Source,
  transform: Transform,
  branch: Branch,
  http_request: HttpRequest,
  code: CodeBlock,
  result: ResultBlock,
}
```

Движок и UI читают один и тот же реестр.

## 4. JSON-схема флоу

Источник истины — zod-схемы в `packages/schema`. Типы выводятся из них (`z.infer`), руками дублировать запрещено.

```jsonc
{
  "version": 1,
  "id": "flow_xxx",
  "name": "demo",
  "nodes": [
    {
      "id": "n1",
      "type": "transform",             // ключ реестра
      "position": { "x": 180, "y": 120 },
      "params": { "mode": "map" },     // значения; валидируются по class.params
      "portsOverride": null,           // null = берём из класса; иначе доб. порты сверх дефолтных
      "cssOverride": null              // null = class.defaultCss; иначе строка CSS
    }
  ],
  "edges": [
    {
      "id": "e1",
      "source": "n1", "sourcePort": "out0",
      "target": "n2", "targetPort": "in0"
    }
  ]
}
```

Правила валидации (zod + ручные инварианты):
- `type` существует в реестре.
- `sourcePort`/`targetPort` существуют у соответствующих нод (с учётом `portsOverride`).
- В один `targetPort` входит максимум одно ребро.
- Граф — DAG (циклы запрещены). Проверка при валидации и перед запуском.
- `params` проходят схему `class.params` (required, типы, enum-опции).

## 5. Движок (`packages/engine`)

Запуск workflow:
1. Валидация графа (schema + инварианты + DAG).
2. Топологическая сортировка.
3. Нода исполняется, когда на **всех подключённых входах** лежит JSON (wait-all в движке).
4. `inputs` собираются из входящих рёбер → `new Block().run(inputs, node.params, ctx)` → `outputs` раскладываются по исходящим рёбрам.
5. Пустой out-порт (ключа нет в результате) = по этой ветке данные не пошли — нижестоящая нода по этому входу останется неготовой.
6. **Final-блок** (`type: "result"`) — нода без выходов; её вход фиксируется как результат запуска.

RunContext (MVP): `{ log(msg), signal }` (для отмены). Без БД, без секретов-хранилища — позже.

Процесс-раннер: отдельный `child_process` на запуск. Протокол web↔runner — JSON-сообщения по stdio или локальному IPC:
- web → runner: `{ cmd: "run", flow }`
- runner → web: `{ event: "node:start"|"node:done"|"node:error"|"flow:done", nodeId?, output?, error? }`
Стримить события в UI (прогресс по нодам). Детали транспорта — на выбор агента, но протокол зафиксировать типами в `packages/schema`.

## 5a. Code-блок (исполнение пользовательского кода)

Встроенный тип `code`. Пользователь пишет **тело функции** в Monaco; код хранится в `node.params.code`. Это единственный блок, чей код приходит из флоу.

Исполнение:
- `node:vm` (`vm.createContext` + `vm.Script`), **таймаут** на запуск, отмена по `ctx.signal`.
- Контекст-sandbox содержит **только** то, что мы явно кладём, — объект `env`. Никакого ambient-доступа: нет `require`, `process`, `fs`, глобального `fetch`, если мы их не положили.
- `env` определяется в самом классе Code-блока (наш код) — это точка, где прокидываются нужные функции:

```ts
// packages/blocks/src/code.ts
const env = {
  inputs,                 // { in0: json, ... }
  params,                 // значения ноды (кроме самого code)
  log: ctx.log,
  fetch,                  // прокинули сеть осознанно
  // require/fs/process НЕ прокидываем
}
```

- Контракт кода пользователя: доступны переменные из `env`; возвращает `{ out0: json }`. Пример тела:

```js
const data = inputs.in0
const res = await fetch(params.url).then(r => r.json())
return { out0: { ...data, res } }
```

- Ошибки/таймаут Code-блока → `node:error` с сообщением, флоу останавливается на этой ноде.

Безопасность: `vm` — изоляция «по белому списку окружения», не крепость. Достаточно для локального/командного (доверенного) использования. При появлении недоверенных юзеров Code-блок переносится в `isolated-vm` или отдельный процесс — контракт `env` сохраняется.

## 6. Фронтенд (`apps/web`)

- **Next.js App Router**, TypeScript strict.
- **shadcn/ui** — все контролы. Спецификация компонентов и соглашения: https://ui.shadcn.com/llms.txt (прочитать перед генерацией UI).
- **Холст:** React Flow (`@xyflow/react`). Кастомная нода рендерит динамические in/out порты (handles), применяет scoped CSS. Связи, зум, пан, выбор — из коробки.
- **Редактор кода/CSS блока:** Monaco (`@monaco-editor/react`), языки `javascript` и `css`.
  - Для **Code-блока** JS-редактор editable, пишет в `node.params.code`. Желательно подсказать тип `env` (d.ts/типизация для автокомплита `inputs`/`params`/`fetch`/`log`).
  - Для остальных типов кода нет (их `run` в TS-классах) — вкладку кода не показывать.
  - CSS-редактор editable для любой ноды, пишет в `node.cssOverride`.
- **Правая панель (авто-UI params):** строит форму из `class.params`:
  - `string → Input`, `number → Input[type=number]`, `boolean → Switch`,
  - `enum → Select` (по `options`), `json → Textarea` (с валидацией).
  Значения пишутся в `node.params`. Поддержать `required`, `default`.
- **Левая панель:** палитра из реестра, сгруппирована по `category`.
- **Топбар:** Run / Save, индикатор рантайма, статус запуска.
- **Тема:** `next-themes`, toggle light/dark, переменные согласованы с shadcn.
- **i18n:** `next-intl`. Все строки UI — через словари. Языки на старте: `ru`, `en`. Переключатель языка в топбаре.

## 7. Custom CSS без протечек (обязательно)

Каждая нода оборачивается контейнером с атрибутом `data-node-id="<id>"`. CSS из `cssOverride`/`defaultCss` применяется **только** внутри scope этой ноды. Реализация на выбор:
- префиксовать селекторы `[data-node-id="n1"] .node { ... }` при инъекции, **или**
- CSS-переменные на контейнере + фиксированный внутренний CSS ноды.

Запрещено: глобальная инъекция CSS блока без scope (один блок не должен влиять на другие/на доску).

## 8. Структура монорепо

```
/apps/web               Next.js: холст, панели, API-роут запуска
/packages/schema        zod-схемы flow + протокол runner; z.infer типы
/packages/blocks        Block, наследники, registry
/packages/engine        валидация, топосорт, process-runner, исполнение
```

Пакеты — workspace (pnpm). `schema` и `blocks` импортируются из `web` и `engine`.

## 9. MVP (объём первой версии)

Включено:
- 6 блоков: `Source` (отдаёт заданный JSON), `Transform` (map/filter над JSON), `Branch` (1 вход → 2 выхода по условию), `HttpRequest` (GET/POST → JSON), `Code` (пользовательский JS в vm + env, см. §5a), `Result` (финальный).
- Холст: добавить ноду из палитры, соединить порты, двигать, удалять.
- Правая панель: авто-UI params + редактор CSS ноды.
- Save/Load флоу как JSON-файл.
- Run: отдельный процесс, wait-all, стрим событий по нодам, показ результата из `Result`.
- Тема light/dark, языки ru/en.

НЕ включено (следующие итерации): per-block отдельный процесс, items/батчинг, секреты/credential-store, персист в БД, undo/redo, кастомные порты в инстансе (`portsOverride` оставить в схеме, но UI — позже), создание блоков из UI.

## 10. Этапы

1. **Каркас:** монорепо, схема (zod), реестр с 1-2 блоками, пустой engine, Next.js с темой + i18n.
2. **Холст:** React Flow, кастомная нода с портами, палитра, рёбра, save/load JSON.
3. **Панель блока:** авто-UI params, Monaco CSS-редактор, scoped CSS.
4. **Движок:** валидация + DAG + топосорт + исполнение в памяти (без процесса) → тесты.
5. **Process-runner:** вынос в child_process, протокол событий, стрим в UI.
6. **Блоки MVP:** добить все 6 (включая Code-блок с vm+env и таймаутом), Result-блок, показ результата.
7. **Полировка:** ошибки валидации в UI, пустые состояния, i18n-строки.

## 11. Критерии приёмки

- `pnpm -w typecheck` и `pnpm -w lint` проходят; strict TS.
- Невалидный флоу (цикл, битый порт, несошедшиеся params) отклоняется с внятной ошибкой — в API и в UI.
- Запуск демо-флоу (`Source → Transform → Result`) в отдельном процессе возвращает корректный результат в `Result`; UI показывает прогресс по нодам.
- CSS одной ноды не влияет на другие ноды и на доску (есть тест/проверка scope).
- Code-блок: код из `params.code` исполняется с доступом только к `env`; `require`/`fs`/`process` недоступны (есть тест); бесконечный цикл обрывается по таймауту; ошибка кода даёт `node:error`, а не падение раннера.
- Переключение темы и языка работает без перезагрузки; нет захардкоженных строк UI.
- Новый блок добавляется одним TS-классом + одной строкой в реестр; UI и движок подхватывают его без прочих правок.

## 12. Запреты

- Пользовательский код исполняется ТОЛЬКО в Code-блоке и ТОЛЬКО в vm-контексте с явным `env`-whitelist и таймаутом. Нигде больше кода из флоу не исполнять. `run` TS-классов строкой не хранить.
- Не тащить node-only/browser-only импорты на уровень модуля в `packages/blocks`.
- Не дублировать типы мимо zod-схем.
- Не инъектить CSS блока глобально.
- Не расширять объём MVP из раздела 9 без запроса.
